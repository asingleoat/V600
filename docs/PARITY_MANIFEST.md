# Python To Zig Parity Manifest

This manifest tracks the function-by-function rewrite from the frozen Python
implementation to Zig. Keep it current while porting behavior. A checklist item
in `plan.md` is not complete if it ports Python behavior and leaves this
manifest stale. Replacement algorithms are not parity evidence unless the user
explicitly approves them as a post-parity divergence.
Numeric acceleration may use documented final-output tolerances instead of
byte-for-byte equality with the Python oracle or with intermediate buffers when
the operation remains traceable to the frozen Python function and the speedup
justifies the measured error.

## Status Vocabulary

- `not-started`: no meaningful Zig implementation.
- `scaffolded`: types or stubs exist, but behavior is incomplete.
- `replay-tested`: deterministic tests cover captured or synthetic behavior.
- `oracle-tested`: Zig output has been compared to Python output.
- `hardware-tested`: relevant scanner or platform hardware was exercised.
- `parity-accepted`: all applicable tests, oracle comparison, and live checks
  are complete.
- `deferred`: intentionally delayed with a recorded reason.
- `blocked`: cannot proceed without specific input or environment.

## Update Rules

1. Add or update rows before checking off related work in `plan.md`.
2. Keep Python source references precise enough to find the oracle quickly.
3. A Python behavior may map to multiple Zig functions; list the important
   Zig symbols rather than hiding behavior behind a module name.
4. Do not use `parity-accepted` unless all applicable replay, oracle, hardware,
   metadata, and platform checks are complete.
5. Zig must match the frozen Python algorithm before a row can be complete. A
   different algorithm is scaffold or deferred work, not function-for-function
   parity. Faster code must still name and preserve the Python function's
   algorithmic dependency, such as OpenCV, SciPy, scikit-image, NumPy, SANE, or
   Epson interpreter behavior.
6. Numeric optimized paths may be accepted with documented final-output
   tolerances instead of byte-for-byte equality with Python output or internal
   floating-point buffers. Record the relevant `max_abs`, RMS/MSE, mismatch
   rate, metadata equality, and speedup at the final preview/export/mask/
   geometry surface.
7. If a behavior is hardware or platform gated, use `replay-tested` until live
   evidence exists.
8. Keep `Evidence` short but concrete: test names, command names, fixture
   paths, hardware output paths, or verification-log entries.
